# コアループとアークの評価フレームワーク案

設計案・2026-11-13。[初期実装と実行方法](../../game/experience/README.md)を追加した。FATHOMの戦闘ラウンド・地下2階到達、共通の抽出器、比較レポート、Studioでの記録閲覧が動作する。以下は今後の計測も含む設計で、全ての指標を実装済みという意味ではない。

目的は、プレイヤーが状況を読み、選び、反応を受け取り、次を試す体験を調べること。ループの回数、攻略の正確さ、継続時間を最大化する設計にはしない。既存の[体験評価とバランス実験](../../game/balance/README.md)へ、時間順の記録と評価単位を追加する。

## 資料から採る定義

出発点はsoy-softwareの[ゲームデザインのコアループ理論](https://soysoftware.sakura.ne.jp/archives/3001)。反復する遊びを小さな単位から見る、という着眼を使う。

参照されているDaniel Cookの原文[Loops and Arcs](https://lostgarden.com/2012/04/30/loops-and-arcs/)では、行動とフィードバックを通じた理解の更新が共通の土台になる。ループは反復によって学びを深める構造、アークは情報や体験を受け取って一区切りになる構造。両者は入れ子にも並行にもなる。したがって、RPG全体を一方へ分類せず、場面ごとに重ねて記述する。

以下はKagura向けの提案で、原典の採点法ではない。アークを物語の文字量に限定せず、初めて階層へ降りる、敵の性質を知る、印章を得る、といった体験も扱う。また、緊張の山谷を表す曲線は「ペーシング」と呼び、ここでのアークと区別する。

`sakurai-game-design`の資料では、[ノーリアクションを排除せよ](https://www.youtube.com/watch?v=EDs5n39sRFc)を反応の検証、[ゲーム性以外の面白さ](https://www.youtube.com/watch?v=OALp2UAe6V4)を評価範囲の確認に使う。判断の多さだけで、操作・探索・物語の価値を代用しない。

## 1. 評価単位を宣言する

ゲームごとの `ExperienceSpec` に、ループ・アーク・関係・測定意図を定義する。コアループを秒単位に固定しない。ボタン入力、判断、ラウンド、遠征は別の単位として数える。

| 対象 | FATHOMでの候補 | 境界と見るもの |
| --- | --- | --- |
| 戦闘ループ | 状況を読む → 行動を予約 → 解決 → 結果確認 → 次の判断 | ラウンド単位。入力の受理と、全員分を解決した結果を区別する |
| 探索ループ | 周囲を見る → 進む/調べる/戻る → 情報と資源が変わる → 次の判断 | 判断単位。既知の通路の移動を、毎回新しい発見とは数えない |
| 遠征ループ | 準備 → 探索と戦闘 → 帰還 → 次の準備 | 遠征単位。途中の戦闘・探索を含む |
| 発見のアーク | 地下2階への初到達 | 未知の場所を知る機会。到達、画面提示、本人の認識を別々に記録する |
| 完結のアーク | 印章を獲得して持ち帰る | 獲得と帰還で体験がどう区切られたか。終了を悪い離脱として扱わない |

これらの関係はグラフとして持つ。遠征が戦闘を「含む」、発見が次の探索判断の「文脈を変える」、演出が入力を「中断する」、音楽と探索が「並行する」、などを明記する。子ループの時間を合計して親と二重計上しない。所要時間には包含時間と自身だけの時間を区別する。

アークには意図を付ける。`discovery / understanding / emotion / closure` などから選び、何を確かめたいかを書く。感情や完結を味わうアークへ、戦術変更を一律に要求しない。単なる別名の敵や乱数の変化も、それだけでは新しい価値としない。

定義の概形は次のとおり。イベント名と条件の構文は、実装時に厳密な型と検証器を定める。

```text
ExperienceSpec
  game / specVersion
  loops[]: id, intent, start, resolution, nextOpportunity, expectedFeedback
  arcs[]: id, intent, entry, payoff, knowledgeKey, repetitionScope
  relations[]: from, to, kind
  measures[]: target, unit, eligibility, evidence, aggregation, desiredRange?
```

一周したという構造の記録と、プレイヤーが理解したという評価は分ける。フィードバックを出しただけで、理解まで完了したループとは判定しない。途中終了した区間には `completed / interrupted / censored` と理由を残す。未到達の任意アークを自動的な失敗にしない。

## 2. まず数えるもの

指標は次の三種類の証拠に結び付ける。Jevのレビューは、それらを読む「モデルによる仮説」として別に置く。

- **ルール上の結果**：入力を受け付けたか、誰に何が起きたか、次に何を選べるか。
- **画面・音の提示**：対応する反応をいつ、どこに出したか。描画を確認しても、本人が気づいたとは限らない。
- **プレイヤーの認識**：何が起きたと理解したか、なぜ次を試したいか。実プレイや短い質問で確認する。

| 指標 | 定義・単位 | 評価時の注意 |
| --- | --- | --- |
| 因果の対応率 | 反応が必要な操作・解決のうち、対応する結果記録がある割合。分子/分母も保存 | HPが変わらない防御や壁への移動にも、適切な反応がありうる。既存のHP監査だけでは足りない |
| 反応の遅延 | 入力→受理、解決→最初の提示、再操作可能になるまでの各ms。中央値とp95 | 演出終了時刻で最初の反応を代用しない。headlessやAPI応答時間から画面の遅延を作らない |
| 入力の負担 | 意味のある解決1回あたりの入力数、予約の取消・修正数 | 入力数を減らすだけでは、選ぶ楽しさも消しうる。手動とまとめ入力を別に集計する |
| 選択による結果の差 | 同じ局面から別の合法手を試した際の、被害・資源・位置・情報などの差 | 最善手の正解率にしない。単なる乱数差や、どの指標を重要としたかも残す |
| 理解の転移 | フィードバックを受けた後、別の関連場面でも結果や原因を説明できる割合 | 攻略の成功と別に確認する。行動ログだけでは人の理解を実測できない |
| 初めての提示 | プレイヤーにとって未提示だった `knowledgeKey` の数と提示までの時間 | 未提示は未知の代理指標。提示済みも、理解・記憶済みとは限らない |
| 既知の内容に拘束された時間 | 既に提示したアークの再提示により、進行操作が強制的に止まったms | 自分で読み返す、眺める時間は分ける。再提示の価値を時間だけで否定しない |
| アークの受け取り | 初見/再見別の到達、提示、認識、完結への納得 | 数字の増加や新規セル数を、驚き・感動の点数へ変換しない |
| ループへの接続 | アークを提示した後の関連する判断機会で、その情報を参照した記録 | 参照の有無は効果の手掛かり。因果の確定には比較条件が必要。接続が意図されないアークには適用しない |

これらの方向は一律に「高いほど良い」にはしない。例えば選択による差が大きすぎれば失敗が重く、反応を短縮しすぎれば結果が読めない。目標範囲は対象プレイヤー・場面・機器を決めてから置く。

ペーシングには、被害・残り資源・入力拘束・回復機会の時系列を重ねる。被害が続いた区間の長さ、回復機会までの間隔などを調べる。ただし、これらの名前は「被害」「資源」とし、本人の申告がないデータを恐怖・緊張・達成感の実測とは呼ばない。

継続・再挑戦を調べる場合も、自由に終えられる人間のプレイを対象にする。最後まで走るよう命令したautoplayの周回率を、もう一度遊びたい気持ちに置き換えない。

## 3. 記録の契約

### イベントと時計

構造化したイベントを追記する。表示文言の解析だけで、戦闘開始・発見・完結を推測しない。

```text
ExperienceEvent
  version, runId, eventId, sequence
  type, source, actor
  causeIds[]
  loopInstanceIds[], arcInstanceIds[]
  revision, decisionIndex, simTick?
  presentationMs?, wallMs?
  payload
```

一つの入力から複数の結果が生まれ、複数の予約から一つのラウンドを解決するため、因果の対応は多対多にする。入力の受理、ルールの解決、結果表示の開始、再操作可能、発見内容の提示などを別イベントにする。描画からの確認は、結果を参照するイベントで追加する。

シミュレーションの進行、表示の時計、壁時計は混ぜない。停止・バックグラウンド・読み込み・プレイヤーの思考・API待ちを識別する。再挑戦の総待ち時間にはロードも含めて内訳を出す一方、入力への反応時間からはプレイヤーの思考を除く。どの区間を分母にしたかを指標へ保存する。

今のautoplayには複数歩を進める操作があるため、判断前後のsnapshotだけでは途中の発見順や表示時刻を復元できない。細かい計測はゲームの遷移側からイベントを出す。欠落やリングバッファの取りこぼしは記録品質の問題として報告する。

### プレイヤーの既知情報

`KnowledgeLedger` は、ゲーム内の既読フラグと独立させる。

```text
KnowledgeLedger
  subjectId, scope, knowledgeKey, contentVersion
  exposures[], recognitionEvidence[], comprehensionEvidence[]
```

FATHOMは[出発時](../../examples/games/dungeon_rpg/sim/world.mbt)に `seen` と `visited` を消す。この処理だけを使うと、同じ人の2回目も初発見に数えてしまう。評価側では周回をまたいだ提示履歴を持つ。知っているか不明な参加者や、記憶を保持しないモデルは、その条件も明示する。

`knowledgeKey` は作者が意味の単位として定める。例えば同じ地図の同じ場所は、敵HP倍率だけを変えても別の発見にしない。ファイル全体のhashは再現性に使い、知識の単位の代わりにしない。提示・認識・理解の履歴は別々に保つ。

評価器は検証のために完全な状態を参照できるが、プレイヤー役には観測可能な情報だけを渡す。周回から持ち越す情報も、過去にそのプレイヤーへ提示されたものを出所付きで扱う。

### 指標と欠測

```text
MeasureResult
  targetId, metricId, value | null, unit
  numerator?, denominator?, eligibleCount
  aggregation, cohort, evidenceKind
  status: observed | not-instrumented | not-applicable | censored
  evidenceEventIds[], reason?
```

表示計測がなければ `value: null, status: not-instrumented` とする。未観測を0msや不一致0件にしない。比較機会がなければ分母0と理由を残す。Jevの信頼度は測定誤差やプレイヤーの満足度の代わりにしない。

runにはゲーム・評価定義・マスターデータ・描画のバージョン、seed、方針、入力経路、保存状態、既知情報の条件を固定して残す。レポートの数値から、元のイベント列と再生位置へ戻れるようにする。

## 4. 比較実験の組み立て

最初は次の三つを独立に調べる。数値は実測してから決め、普遍的な合格線は設けない。

1. **戦闘の入力と反応**：同じ局面で手動予約とまとめ入力を比べる。入力数、選択による差、結果の理解を確認する。結果が似ているのに手間だけ多いなら操作整理の候補となる。まとめ入力で重要な判断まで失う可能性も確認する。
2. **探索の初見と再見**：同じ地図を初めて遊ぶ場合と、既知の場合を分ける。発見の提示、既知の移動に使う時間、戦闘・撤退の判断を比較する。初見の価値と、既知の場所でも残る遊びをそれぞれ調べる。
3. **発見後の遊びの変化**：敵の性質を伝える表現を比較し、次の関連する判断で何が読み取られたかを調べる。戦闘数値は固定する。モデルには操作記録、人間には表示と理解の両方を確認する。

反実仮想の比較は、同じ記録の操作prefixを再生して局面を復元し、そこから合法手を分岐する方法が候補になる。現状のAPIに状態のfork契約はないため、追加設計が必要。行動が変わると乱数の消費順も変わりうる。同seedの差をすべて行動の効果とは扱わず、乱数の対応付けを保証するか、複数条件で分布と不確実性を調べる。

比較する結果はHPだけでなく、MP、回復薬、位置、得た情報などのベクトルで残す。重要とする変化量と比較区間を先に宣言する。行動の多様性や結果の分散を、そのまま選択の面白さにしない。

同じ人に同じ地図を二度見せて、両方を初見として比較することはできない。初見の比較には別参加者か対応する別コンテンツを使う。再見を含む比較では順序・上達・疲労、味方の成長や保存資源も区別する。seedを変えるだけでは、固定地図を知らない人への一般化を検証したことにならない。

集計では、初見/再見、操作方法、方針、機器、技能条件を分け、中央値・裾・人数・試行数を示す。同一人物の多数の入力を独立な参加者として扱わない。対応する条件の差を優先し、不確実性は人間なら参加者、autoplayなら試行単位で見積もる。

## 5. Kaguraへの接続順

実装は次の三段階を提案する。

1. **イベントと区間の抽出**：FATHOMの戦闘1ラウンドと地下2階への初到達を対象に、イベント・区間・既知情報の契約を作る。状態と抽出ロジックを分け、同じイベント列から同じレポートを再生成できるようにする。欠測、取消、停止、途中終了、周回後の再提示を先にテストする。
2. **比較レポートとStudio**：ループ/アークの帯、資源と拘束の時系列、元のイベント・リプレイへのリンクを表示する。既存のマスターデータ編集→Play→比較の経路につなぐ。評価定義はゲームのマスターデータと別リソースに置く。評価のための項目を追加してゲーム側のJSON契約を壊さない。
3. **調整候補の選出**：十分に観測できた指標だけを既存のバランス実験へ渡す。欠測のある必須指標は候補選出を保留する。フィードバックの不整合を他の指標で補償しない。人間の受け取りと、Jevの仮説は独立にレビューする。

実装場所の案は、共通契約と純粋な抽出器を `game/experience/`、記録・比較の実行を `scripts/experience/`、ゲーム固有の意味付けをそのアダプターへ分ける形。既存の[scripts/balance/experience.mjs](../../scripts/balance/experience.mjs)はFATHOMのラウンド監査を行っているため、この機能を残して接続する。共通層に敵や階層の名前を持たせない。

現在の[バランス指標契約](../../scripts/balance/contracts.d.mts)は有限の数値を必須にし、[集計](../../scripts/balance/metrics.mjs)は試行ごとの指標を平均する。この契約へ時系列、欠測、初見/再見をそのまま押し込まない。体験レポートを独立させ、明示的な集約と観測条件を満たした数値だけを調整側へ渡す。

自動調整が扱うのは、宣言した範囲からの逸脱と整合性の問題。最終出力は「ループ72点・アーク81点」ではなく、例えば「手動入力の負担が増えたが判断の差は未確認」「初見の発見は提示できたが認識は未測定」「再見では既知の内容に拘束される時間が長い」という、変更と再検証につながる診断にする。
